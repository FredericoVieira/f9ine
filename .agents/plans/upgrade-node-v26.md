# Plan: Upgrade Node version to stable v26

## Summary

Bump the project's pinned/targeted Node.js version from v22 to the current stable v26 line (v26.7.0 as of 2026-08-23). This is a small Next.js 14 static/blog site with no CI workflows and no Dockerfile — the only places Node version is expressed are `.nvmrc`, the README's minimum-version note, and the `@types/node` devDependency. This is a low-risk, mostly mechanical change.

## Files to change

- `.nvmrc` — currently `v22.15.0`. Update to the target v26 version (e.g. `v22.15.0` → `v26.7.0`, or `v26` if the project prefers floating to latest minor/patch).
- `README.md` — states "Node.js version >= v18.17.0 is required for run this project." Update the minimum version note to reflect the new baseline (decide whether to state `>= v26.0.0` or keep a broad floor — see Risks).
- `package.json` — `devDependencies["@types/node"]` is pinned to `^20`. Bump to `^26` (or the latest `@types/node` major matching the runtime) so type definitions match the new Node target.
- `package-lock.json` — will be regenerated by `npm install` after the `@types/node` bump.

## Steps

1. Confirm the exact target version: run `nvm ls-remote` (or check nodejs.org) to get the latest v26.x.y patch release. As of this planning session it's `v26.7.0`.
2. Update `.nvmrc` to the chosen version string.
3. Update the Node version note in `README.md` to match.
4. In `package.json`, bump `@types/node` from `^20` to `^26`.
5. Install/switch local Node to the new version (`nvm install` reading `.nvmrc`, or `nvm use`) so the environment matches before validating.
6. Run `npm install` to regenerate `package-lock.json` with the new `@types/node` resolution.
7. Re-check `next.config.mjs`, `tsconfig.json`, and `package.json` scripts for any Node-version-specific config — none currently found, but confirm nothing was missed.
8. Grep the repo for any other stray Node version references (e.g. in comments, docs) that weren't caught above.

## Validation strategy

- Type/lint: `npm run lint` (next lint) — confirms nothing broke with the new `@types/node` types.
- Build: `npm run build` — confirms the app builds cleanly under the new Node runtime (run this with the new Node version active, i.e. after `nvm use`).
- Dev smoke check: `npm run dev`, load the site locally, confirm the homepage and a blog post page render (per CLAUDE.md's guidance to verify UI changes in a browser where applicable — here it's a sanity check that the runtime bump didn't break anything, not a feature change).
- No test suite exists in this repo (no `test` script in `package.json`), so no unit/integration test layer applies.

## Risks

- `sharp` (image processing, native bindings) and other native deps must have prebuilt binaries for Node v26 — if not, `npm install` may fail or fall back to a slow source build. Verify `npm install` completes cleanly.
- `@types/node@^26` may introduce type changes that surface new TS errors even if runtime behavior is unaffected — run `npm run build` (which type-checks via Next.js) to confirm.
- No CI pipeline exists to catch environment drift automatically — the only enforcement is `.nvmrc` (relies on developers running `nvm use`) and manual verification.
- If this site is deployed via a platform (e.g. Vercel), the deploy environment's Node version setting is managed outside this repo (typically in project/dashboard settings) and is NOT covered by this plan — flag to the user to update it separately if applicable.

## Out of scope

- Any CI/CD configuration — none exists in this repo.
- Docker — no Dockerfile present.
- Upgrading other dependencies (Next.js, React, etc.) beyond what's needed for Node v26 compatibility.
- Changing the deployment platform's configured Node runtime version (outside repo scope; flag to user).
